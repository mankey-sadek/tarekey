# في طريقك 🚗

باك إند لتطبيق طلب رحلات زي أوبر، مكتوب بـ Node.js و TypeScript، ومعاه نموذج تفاعلي للواجهة (شاشات الزبون والكابتن).

| | |
|---|---|
| سواقين متزامنين | **5,000**، متجرّب فعلاً بـ 5,000 اتصال WebSocket |
| تحديث المكان | **WebSockets** |
| التخزين | **In-Memory**، مفيش قاعدة بيانات في مسار اللوكيشن |
| البحث | **H3 Spatial Indexing** |
| سباق القبول | **Conditional Update** على status و version |
| دورة الرحلة | **State Machine** |
| اللي بيحصل بعد الرحلة | **Message Queue** للدفع والإشعارات والتقييم والحسابات |

## التطبيقين

| | لينك التجربة (GitHub Pages) | على السيرفر بتاعك |

| 🧍 تطبيق الزبون | https://mankey-sadek.github.io/tarekey/rider.html | `http://localhost:8080/rider` |
| 🚗 تطبيق الكابتن | https://mankey-sadek.github.io/tarekey/captain.html | `http://localhost:8080/captain` |

- كل تطبيق شاشة كاملة على الموبايل، وتقدر **تثبته** (PWA): افتح اللينك من كروم واختار «Install app» أو «إضافة إلى الشاشة الرئيسية». على آيفون: من سفاري ← مشاركة ← «إضافة إلى الشاشة الرئيسية».
- نسخة GitHub Pages شغالة بمحاكاة جوه الصفحة (مفيش سيرفر هناك): تطبيق الزبون بيلاقي كباتن وهميين، وتطبيق الكابتن بيجيله طلبات من زباين وهميين كل ~٩ ثواني وهو أونلاين.
- النسخة اللي على السيرفر (`npm run dev`) متوصلة بالسيرفر الحقيقي: افتح `/rider` على جهاز و`/captain` على جهاز تاني (نفس الواي فاي: `http://IP-الكمبيوتر:8080/rider`) وهتلاقي الرحلة ماشية بينهم.
- النشر على GitHub Pages أوتوماتيك مع كل push على `main` (`.github/workflows/pages.yml`): بيشغل الاختبارات وبعدين يبني `ui/dist`.

## التشغيل

```bash
npm install
npm run dev         # ⭐ السيرفر + محاكاة مستمرة، وافتح http://localhost:8080 تشوف العمليات لايف
npm test            # 25 اختبار: السباق، الـ state machine، H3، الطابور، رحلة كاملة على WebSocket
npm run test:ui     # 4 اختبارات شاشات في Chromium: رحلة كاملة زبون + كابتن، إلغاء، ورفض
npm run sim         # سيميوليتر في الترمينال: 60 سواق و5 زباين على السيرفر الحقيقي
npm run bench       # اختبار حمل للـ Location Service بـ 5,000 سواق
npm run bench -- --ws   # نفس الاختبار بـ 5,000 اتصال WebSocket حقيقي
npm start           # السيرفر على المنفذ 8080
npm run ui:build    # يبني الواجهات في ui/dist: rider.html و captain.html و fi-tari2ak.html (الاتنين جنب بعض)
```

### اختبارات الشاشات (`npm run test:ui`)

بتفتح تطبيق الزبون وتطبيق الكابتن في متصفح حقيقي (Playwright + Chromium) متوصلين بالسيرفر الحقيقي، وبتدوس على الزراير زي المستخدم بالظبط:
- كل الصفحات (`/` و `/rider` و `/captain` و `/apps` و `/prototype`) بتفتح من غير أخطاء JavaScript.
- رحلة كاملة: تسجيل ← طلب ← الكابتن يقبل ← وصلت ← ابدأ ← إنهاء ← تقييم ٥ نجوم، وبعدها نتأكد إن الحسابات اتسجلت للكابتن والمنصة.
- الزبون يلغي والعرض لسه عند الكابتن، فالعرض يختفي من عند الكابتن.
- الكابتن الوحيد يرفض، فالزبون يشوف «مفيش كباتن قريبين».

الخرايط والطرق (OSM و OSRM و Nominatim) بتتقفل في الاختبار، عشان مايعتمدش على النت. أول مرة على جهاز جديد نزّل المتصفح بـ `npx playwright install chromium`.

على GitHub، الـ workflow اللي في `.github/workflows/ci.yml` بيشغل كل الاختبارات دي لوحده مع كل Pull Request.

## لوحة العمليات المباشرة (`npm run dev`)

بتشغّل السيرفر الحقيقي ومعاه 80 سواق وهمي بيتحركوا، وزبون جديد بيطلب رحلة كل ~2.5 ثانية. افتح `http://localhost:8080`:
- **الخريطة**: كل سواق (أبيض = متاح، أزرق = في رحلة)، الزباين المستنيين (برتقالي)، وخلايا H3 بتنوّر لما السيرفر يدوّر على أقرب سواق.
- **العدّادات**: سواقين أونلاين، تحديثات اللوكيشن في الثانية، سباقات اتحلت بالـ CAS، الرحلات في كل مرحلة، إيراد المنصة.
- **سجل الأحداث**: كل رسالة على الطابور (طلب، عرض، قبول/رفض CAS، تغيير حالة، دفع، حسابات، إشعارات، تقييم) مع فلاتر.
- **الرحلات** و**الحسابات**: جداول بالرحلات الشغالة وقيود الدفع.

اللوحة متوصلة بالسيرفر بـ `ws://host/ws?role=monitor`، وبتاخد صورة كل ثانية + كل حدث على الطابور.
**شاشات الزبون والكابتن متوصلة بالسيرفر** على `http://localhost:8080/app`: اطلب رحلة من شاشة الزبون، أو خلي الكابتن أونلاين واستقبل طلبات حقيقية (من زباين المحاكاة كمان) وقبلها — وتابع نفس الرحلة في لوحة العمليات. نفس الشاشات بمحاكاة داخلية (من غير سيرفر) موجودة على `/prototype`. تقدر تغيّر العدد/السرعة: `DRIVERS=200 SPEED=100 npm run dev` (على ويندوز: `set DRIVERS=200&& npm run dev`).

## تقسيم الخدمات

```
 ┌──────────────┐     ┌──────────────┐
 │ أبلكيشن الكابتن│     │ أبلكيشن الزبون │
 └──────┬───────┘     └──────┬───────┘
        │   WebSocket (قناة مفتوحة)   │
 ┌──────▼────────────────────────────▼──────┐
 │            WebSocket Gateway             │  stateless، يتعمله scale أفقي
 └──┬──────────────┬───────────────┬────────┘
    │ location     │ accept/decline│ arrive/start/complete/cancel/rate
 ┌──▼─────────┐ ┌──▼────────────┐ ┌▼─────────────┐
 │ Location   │◄┤   Dispatch    ├►│    Trip       │
 │ Service    │ │   Service     │ │   Service     │
 │ (H3 + RAM) │ │ (توزيع الطلبات)│ │ (FSM + CAS)   │
 └────────────┘ └───────▲───────┘ └──────┬────────┘
                        │ trip.requested │ trip.completed / cancelled / status_changed
                ┌───────┴────────────────▼────────────────┐
                │              Message Queue              │
                └──┬──────────┬──────────┬──────────┬─────┘
             ┌─────▼───┐ ┌────▼─────┐ ┌──▼─────┐ ┌──▼────────┐
             │ Payment │ │Notifica- │ │ Rating │ │Accounting │
             │         │ │  tions   │ │        │ │ (قيد مزدوج)│
             └─────────┘ └──────────┘ └────────┘ └───────────┘
```

| الخدمة | الملف | مسؤوليتها |
|---|---|---|
| WebSocket Gateway | `src/gateway/wsGateway.ts` | يستقبل رسايل الأبلكيشن ويحوّلها لنداءات على الخدمات، ويوصّل الأحداث للي متصل عنده |
| Location | `src/services/location/` | أماكن السواقين في الميموري متفهرسة بـ H3، وحالة كل سواق (متاح أو مشغول) |
| Dispatch | `src/services/dispatch/` | يدوّر على أقرب سواقين، ويبعتلهم العرض، ويحل سباق القبول، ولو العرض خلص وقته ينتقل للي بعدهم |
| Trip | `src/services/trip/` | صاحب بيانات الرحلة الوحيد: الـ state machine والـ conditional update |
| Payment | `src/services/payment/` | يخصم من الزبون بـ idempotency key، فمفيش خصم مرتين |
| Notification | `src/services/notification/` | يحوّل الأحداث لإشعارات |
| Rating | `src/services/rating/` | متوسط تقييم كل كابتن |
| Accounting | `src/services/accounting/` | قيد مزدوج: الزبون (−)، الكابتن (+80%)، المنصة (+20%)، والمجموع صفر |

كل الخدمات بتشتغل دلوقتي في process واحد عشان التجربة تبقى سهلة (`src/app.ts`)، لكن مفيش خدمة بتعرف تفاصيل خدمة تانية:
- **التواصل الـ async** بيعدّي على الطابور، والعقود (topics وشكل الرسايل) موجودة في `src/shared/contracts.ts`.
- **التواصل الـ sync** بيعدّي على interface صغير (مثلاً `LocationService.findNearest`)، وده يتبدل بـ gRPC أو HTTP لما الخدمة تتفصل في process لوحدها.

## ١. اللوكيشن: WebSocket وتخزين في الميموري

الكابتن بيفتح اتصال واحد `ws://host/ws?role=driver&id=...` ويبعت عليه `{"type":"location","lat":..,"lng":..}` كل ثانية لـ 3 ثواني.
- السيرفر بيخزن **آخر مكان بس** في `Map` في الميموري، من غير قاعدة بيانات ومن غير ما يرد على كل رسالة.
- لو السواق بعت أسرع من اللازم، الرسايل الزيادة بتتجاهل (throttling).
- لو الاتصال فصل أو الـ ping مارجعش، السواق بيتشال من الفهرس. ولو بطّل يبعت أكتر من 30 ثانية، الـ stale eviction بيشيله.

## ٢. H3: أقرب سواق في أقل وقت

بدل ما نحسب المسافة لـ 5,000 سواق في كل طلب، بنقسم الخريطة لخلايا سداسية بنظام H3 (دقة 9، يعني ضلع الخلية حوالي 174 متر):

```
cells:   H3 cell → Set<driverId>      ← لما السواق يعدّي من خلية لخلية: شيل من القديمة وحط في الجديدة، O(1)
drivers: driverId → {lat, lng, cell, status}
```

لما الزبون يطلب، بندور على خلية الزبون، وبعدين الحلقة اللي حواليها (`gridDisk k=1`)، وبعدها k=2، وهكذا لحد ما نلاقي عدد كفاية. بعدها بنوسّع حلقة كمان واحدة، لأن الشكل السداسي مش دايرة مظبوطة، وبنرتب النتيجة بالمسافة الحقيقية (Haversine). الاختبار `test/location.test.ts` بيقارن النتيجة بالبحث الكامل على 5,000 سواق.

## ٣. سباق القبول: Conditional Update

الطلب بيتبعت لأقرب 3 كباتن في نفس الوقت، فممكن اتنين يدوسوا "قبول" في نفس الملّي ثانية. الاتنين هيقروا الرحلة وهي `requested` و `version = 1`، والحل إن الكتابة تبقى مشروطة:

```sql
UPDATE trips
   SET status = 'accepted', driver_id = $driver, version = version + 1
 WHERE id = $trip AND status = 'requested' AND version = $seenVersion;
-- rowCount = 1 → كسبت    |    rowCount = 0 → حد سبقك (already_taken)
```

- واحد بس هينجح. التاني بياخد `already_taken`، وبيوصله `offer_withdrawn`، وبيرجع متاح على طول.
- قبل الـ UPDATE كمان بنحجز السواق نفسه بنفس الفكرة (`tryReserve`: متاح ← مشغول)، عشان مايقبلش رحلتين في نفس الوقت.
- الكود في `InMemoryTripRepository.compareAndSet`، والجزء اللي بيكتب فيه مفيهوش أي `await`، فهو ذري في Node.js زي صف واحد في قاعدة البيانات.
- الاختبار `test/race.test.ts` بيجرب 50 سواق بيكتبوا في نفس اللحظة، وسواقين بيقبلوا مع بعض 30 مرة، وسواق واحد بيقبل رحلتين في نفس الوقت، والزبون بيلغي في نفس لحظة "وصلت". وكل ده مع تأخير عشوائي يحاكي قاعدة بيانات حقيقية.

## ٤. الرحلة كـ State Machine

```
requested ──accept──▶ accepted ──arrive──▶ driver_arrived ──start──▶ started ──complete──▶ completed
    │                    │                       │
    └──────cancel────────┴─────────cancel────────┴──▶ cancelled
```

- مفيش تخطي، يعني مينفعش تبدأ الرحلة قبل ما توصل. ومفيش رجوع لورا.
- الإلغاء مقفول بعد ما الرحلة تبدأ.
- كل انتقال بيعدّي على CAS، فلو اتنين غيّروا الرحلة في نفس اللحظة، واحد بس بيكسب، والتاني بيعيد القراءة ويتأكد إن الانتقال لسه مسموح.
- الكود في `src/services/trip/stateMachine.ts`.

## ٥. بعد الرحلة: الطابور

لما الكابتن يدوس "إنهاء"، السيرفر يحدّث الحالة ويرد عليه فوراً، ويبعت حدث `trip.completed` على الطابور. بعدها كل خدمة بتشتغل لوحدها:

- **Payment**: بيخصم من الزبون، ولو بوابة الدفع فشلت بيعيد المحاولة (retry مع backoff). ولو نفس الرسالة وصلت مرتين مابيخصمش مرتين.
- **Accounting**: بيسجل القيود بعد ما الدفع ينجح.
- **Notifications**: بيبعت الإشعارات للزبون والكابتن.
- **Rating**: بيفتح التقييم، ولما الزبون يقيّم بيحدث متوسط الكابتن.

كل خدمة ليها consumer group خاص بيها، فلو الإشعارات وقعت الدفع مايتأثرش، والرسايل اللي فشلت بعد كل المحاولات بتروح Dead Letter Queue. الطابور الحالي في الميموري (`src/shared/messageBus.ts`)، وفي الإنتاج نفس الـ interface يتنفذ فوق RabbitMQ أو Kafka أو Redis Streams.

## بروتوكول الـ WebSocket

| من | الرسالة |
|---|---|
| الكابتن ← السيرفر | `location` · `accept` · `decline` · `arrive` · `start` · `complete` · `cancel` · `history {limit, before}` |
| الزبون ← السيرفر | `request_trip {pickup, dropoff, rideType, pickupName, dropoffName, promoCode}` · `cancel` · `rate {stars}` · `history {limit, before}` · `check_promo {code}` |
| السيرفر ← الاتنين | `hello` · `trip_offer` · `offer_withdrawn` · `trip_update` · `notification` · `earning` · `ack` · `error` |

أي رسالة فيها `reqId` بيرجع ردها بنفس الـ `reqId`.

### تاريخ الرحلات وأكواد الخصم

- `history` بترجع رحلات الزبون (أو الرحلات اللي اتعينت للكابتن) الأحدث الأول، ومعاها أسامي الأماكن وبيانات الكابتن واسم الزبون والتقييم. الكابتن بياخد كمان `netCents` (صافيه بعد العمولة من خدمة الحسابات). للصفحة اللي بعدها ابعت `before` = `createdAt` بتاع آخر رحلة.
- التقييم بيتحفظ على الرحلة (`riderStars`) بـ Conditional Update، فمينفعش تتقيّم مرتين.
- أكواد الخصم: `FITARI2AK` (٢٠٪ لحد ٣٠ ج.م) و `WELCOME50` (٥٠٪ لحد ٥٠ ج.م، لأول رحلة بس). كل زبون يستخدم الكود مرة واحدة، و`fareCents` هي اللي الزبون بيدفعها بعد الخصم (`discountCents`).
- في التطبيق: «رحلاتي» فيها فلتر (الكل/مكتملة/ملغية) وتفاصيل كل رحلة بالإيصال، تقييم متأخر، «اطلب نفس الرحلة تاني»، ومشاركة الإيصال. المحفظة رصيدها حقيقي (بيقل لما تدفع منها، وفيها شحن تجريبي). المساعدة بتبعت طلب دعم مربوط برحلة، وفيها أرقام الطوارئ. الكابتن عنده تاريخ فيه الرحلات الملغية، أرباح النهاردة وآخر ٧ أيام، ونسبة قبول محسوبة فعلاً.

## للإنتاج (الخطوات الجاية)

- **التوثيق (Auth)**: JWT في الـ handshake بدل `?id=`.
- **قاعدة البيانات**: Postgres للرحلات (نفس الـ UPDATE المشروط اللي فوق) بدل `InMemoryTripRepository`.
- **الطابور**: RabbitMQ أو Kafka بدل `InMemoryMessageQueue`، مع outbox pattern عشان الحدث مايضيعش لو السيرفر وقع بعد الـ UPDATE.
- **أكتر من سيرفر**: نقسّم الـ Location Service حسب خلية H3 أكبر (دقة 4 أو 5)، كل shard مسؤول عن منطقة. أو نستخدم Redis كـ in-memory مشترك بين السيرفرات.
- **الواجهة**: نوصّل `ui/` بالسيرفر ده بدل المحاكاة اللي جواها.
